# Weekly-note snapshot consistency — proposal and interleaving test specification (v7; UNRESOLVED)

Current contract (v3, commit b74676ae, four green nightlies): the note is produced once per nightly with `as_of = generated at`; the checker recounts LIVE under the original window/acceptance rules; a store change between production and check legitimately stops the chain. `created_at <= as_of` is NOT a snapshot and is not to be reintroduced.

Proposal (needs its own source/DB-interaction review before activation): producer and checker share ONE PostgreSQL REPEATABLE READ snapshot by running inside one transaction opened by a small coordinator: `BEGIN ISOLATION LEVEL REPEATABLE READ READ ONLY; SELECT pg_export_snapshot();` → the producer counts in that transaction; the checker attaches with `SET TRANSACTION SNAPSHOT '<id>'` in its own transaction within the coordinator's lifetime. Both then see the same committed set regardless of concurrent inserts. Alternatives: (a) a single process does both counts in one transaction (simplest; loses process separation); (b) count from a materialized daily table written once per run (changes the accepted-event definition — rejected).

Interleaving test specification (to run against a disposable cluster, not production): T1 = producer count; concurrently T2 inserts an accepted row with created_at inside the window; T3 = checker count. Without the shared snapshot: T1 ≠ T3 (chain stops — current behavior). With the shared snapshot: T1 = T3 and the row appears in the next nightly. Also test: exported snapshot expiry (coordinator exits early → checker must fail closed, never fall back to a live count silently), and registry-file changes between the two reads (still a mismatch by design).
